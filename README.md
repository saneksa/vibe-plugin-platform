# VIBE Plugin Platform

**Плагины для браузерного SPA.** Загружаете виджет или приложение zip-архивом — оно появляется на холсте в изолированном iframe, вызывает `hostAPI` и обновляется по версиям без потери данных.

Репозиторий даёт два независимых npm-пакета:

| Пакет | Что это |
| --- | --- |
| `contracts/` → `@vibe/plugin-contracts` | То, что вы подключаете в своём приложении: протокол обмена, валидация архивов, SDK для авторов плагинов, рантайм хоста, conformance-тесты и CLI |
| `demo/` → `vibe-plugin-demo` | Готовое работающее демо: сервер на двух origin, холст с плитками, полноэкранные приложения и шесть примеров плагинов |

От вашего приложения нужен один интерфейс `HostAdapter` (9 методов). Изоляцию, RPC, версионирование и состояние раскладки писать не нужно — они приходят из пакета. Демо показывает, как это выглядит в работе, и запускается одной командой.

## Что здесь можно сделать

- Загрузить плагин архивом с `manifest.json`: манифест, версия протокола, пути файлов и контрольные суммы проверяются **до распаковки**.
- Добавить сколько угодно виджетов на тайловый холст — окна раскладываются автоматически и не перекрываются; пропорции меняются перетаскиванием разделителя или стрелками с клавиатуры.
- Удалить ненужный виджет кнопкой × в заголовке плитки или через контекстное меню заголовка.
- Открыть приложение на весь экран с собственным роутингом, back/forward и deep-link'ами.
- Обновить плагин до новой версии и откатиться обратно: идентификатор экземпляра, позиция на холсте и данные в `host.storage` сохраняются.
- Выдать плагину ровно те права, которые он запросил (`capabilities`), и отрезать ему доступ к DOM хоста.
- Переключить тему хоста: выбор сохраняется, а плагины с правами `theme.read` и `events.read` перекрашиваются вместе с ним.
- Написать плагин на любом фреймворке: чистый TypeScript, React и Vue в примерах используют один и тот же SDK.
- Проверить совместимость своего хоста conformance-тестами и прогнать полный сценарий end-to-end.

## Требования и запуск

Нужны **Node ≥ 24** (пакет отдаёт `.ts`-исходники и CLI использует нативную поддержку TypeScript; проверено на `v24.8.0`), npm и Chromium для тестов.

```sh
git clone https://github.com/saneksa/vibe-plugin-platform.git
cd vibe-plugin-platform

cd contracts && npm install && cd ..
cd demo && npm install
npx playwright install chromium   # только для тестов
npm run dev
```

Откройте **http://localhost:4000**. Одна команда `npm run dev` поднимает хост, REST API и статику плагинов в одном процессе:

| Адрес | Что отдаёт |
| --- | --- |
| `http://localhost:4000` | SPA-хост, `/api/plugins`, `/api/meta`, а также HTML для `/` и `/app/<iid>/<path>` |
| `http://localhost:4001` | статика плагинов `/plugins/<id>/<version>/…` — отдельный origin с CSP |

Чтобы на холсте появились плагины, соберите примеры и загрузите архивы зоной «Загрузить zip» в каталоге слева — или просто перетащите их в окно:

```sh
npm run examples:pack   # → examples/*/dist/<id>-<version>.zip
```

Дальше: нажмите ＋ у плагина в каталоге — на холсте появится плитка; загрузите вторую версию того же плагина → «Обновить» или «Откатить»; откройте `notes-app` на весь экран и походите по его роутам.

## Архитектура

```
  archive.zip
  (manifest.json · checksums.json · index.html · dist/ · assets/)
        │  POST /api/plugins (multipart)
        ▼
  ┌─────────────────────────── :4000 ───────────────────────────┐
  │  сервер: лимит → имена → манифест → версия → checksums       │
  │          → ТОЛЬКО ПОТОМ распаковка → registry.json          │
  │  GET /api/plugins → { versions, activeVersion }              │
  │  PUT /api/plugins/:id/active → обновление / откат            │
  │  GET /api/meta   → политика версий                           │
  └───────────────────────────┬─────────────────────────────────┘
                              │ SPA + JSON
                              ▼
  ┌─────────────────────────── хост (:4000) ────────────────────┐
  │  HostAdapter (9 методов)  ──  createFrameManager(...)        │
  │  каталог плагинов · холст виджетов · приложение на весь экран │
  │  состояния: host.instances.v1 + host.layout.v1                │
  └───────────────────────────┬─────────────────────────────────┘
                              │  <iframe sandbox> · отдельный origin
                              ▼
  ┌─────────────────────────── :4001 ───────────────────────────┐
  │  плагин: свой realm, свои CSS/@font-face/глобалы             │
  │  window.__VIBE_BOOT__ → SDK → createPlugin({ mount, routes }) │
  └───────────────────────────┬─────────────────────────────────┘
                              │  postMessage RPC
                              ▼
   hello → ready(caps) → rpc(method, ctx) → rpc.result
   event · navigate · route · lifecycle · error
```

Плагин не может достать DOM хоста: origin'ы разные, iframe в sandbox, а каждое сообщение проверяется по `origin`, `source` и `iid`. Проверки, права и таймауты реализованы в `MessageRouter` из `host-core` — он не зависит ни от DOM, ни от HTTP.

## Что где лежит

```
vibe-plugin-platform/
├── contracts/   @vibe/plugin-contracts  ← подключаете в своём приложении
├── demo/        vibe-plugin-demo        ← пример интеграции, который можно запустить
└── docs/        проектная документация
```

Экспорты `contracts/`:

| Подпуть | Назначение |
| --- | --- |
| `protocol` | конверты сообщений, их валидация, мажоры `api`, политика версий |
| `manifest` | схема манифеста, проверка версии протокола, контрольные суммы, защита от zip-slip |
| `sdk` | `createPlugin`, типизированный `HostApi`, RPC-клиент, `routeMatcher` |
| `host-core` | `HostAdapter`, `MessageRouter`, `FrameManager` / `FrameHost`, состояния, BSP-дерево |
| `conformance` | тесты без браузера + browser rig с двумя origin и «вредным» плагином |
| `cli` | `vibe-plugin create / pack / check` |
| `compatibility.json` | единый источник правды о поддерживаемых версиях протокола |

В `demo/` только обвязка: `HostAdapter`, UI, реестр на `registry.json` и примеры плагинов. Переносимых механизмов там нет.

## Как это устроено

**Изоляция.** Каждый экземпляр — iframe с `sandbox="allow-scripts allow-same-origin allow-forms"` на отдельном origin, с CSP (`connect-src 'none'`, `frame-ancestors …`). `allow-same-origin` безопасен потому, что origin плагина не совпадает с origin хоста. `allow-top-navigation` и `allow-popups` запрещены. Стили, шрифты, глобалы и ошибки плагина остаются внутри его фрейма.

**Обмен с хостом.** Запросы отправляет плагин, хост отвечает и рассылает события. Поле `api` содержит только мажор протокола (`"1"` или `"2"`); новые возможности внутри мажора добавляются как `caps`. Таймаут RPC — 5 секунд, handshake — 10. Перед каждым вызовом ядро проверяет права.

**Версии.** Версия плагина, версия SDK, мажор протокола и версия хоста — разные величины. Внутри одного мажора протокол только дополняется; несовместимое изменение означает новый мажор и отклоняется при установке. Активная версия хранится на сервере: загрузка архива её не меняет, а обновление и откат выполняются явным запросом. Экземпляр при этом не пересоздаётся — данные и позиция остаются на месте.

**Холст и приложения.** Виджеты раскладываются деревом сплитов (`h` — рядом, `v` — друг под другом) и занимают весь холст. Приложения открываются на весь экран, в дерево не входят и имеют URL вида `/app/<iid>/<path>` с работающими back/forward и восстановлением после перезагрузки.

**Тема и уведомления.** Тема хоста — класс `light` на `<html>`; выбор сохраняется в `localStorage`. `DemoHostAdapter` отдаёт её плагинам через `theme.get`, а переключатель рассылает `theme.changed` через `fm.publish` — плагины с правами `theme.read` и `events.read` перекрашиваются на лету. `notify.show` из плагина показывается тостом через `onNotify` адаптера.

**Плагины.** Автор реализует `mount(el, host)`, а для приложения ещё `routes`. `pack` собирает бандл, добавляет `window.__VIBE_BOOT__`, считает контрольные суммы и делает zip; `check` проверяет архив тем же валидатором, что и сервер.

**Проверки.** `runCoreConformance` прогоняет протокол, версии и раскладку без браузера; `runConformance` поднимает реальный Chromium с двумя собственными origin и проверяет изоляцию. Один и тот же `HostAdapter` работает в трёх конфигурациях: приложение, тесты без браузера, browser rig.

## Написать свой плагин

```sh
npx vibe-plugin create my-widget     # 1. шаблон
cd my-widget
#   2. src/main.ts: createPlugin({ mount(el, host) { … } })
npm run pack                          # 3. сборка + boot + контрольные суммы + zip
npx vibe-plugin check dist/my-widget-1.0.0.zip   # → ok
#   4. «Загрузить zip» в каталоге хоста → ＋ у плагина → плитка на холсте
```

Манифест, права (`capabilities`) и `kind: "app"` описаны в [demo/README.md](demo/README.md). Готовые примеры: ванильный TS, React (TSX), Vue (SFC), приложение с роутингом на react-router и «вредный» виджет.

## Подключить к своему приложению

Единственный класс, который пишете вы — `HostAdapter`: `getMeta`, `getContext`, `grantCapabilities`, `dispatchRpc`, `onNavigate`, `getPluginOrigin`, `getPluginFrameBase`, `getActiveVersions`, `setActiveVersion`.

```ts
const adapter = new MyHostAdapter(config);
const fm = createFrameManager({ adapter });
await fm.restore();                            // сверить активные версии с сервером
const rec = fm.createInstance(descriptor, "widget");
fm.mount(container, rec.iid);
await fm.upgrade("clock", "2.0.0");            // обновление на месте, тот же экземпляр
```

Разбор каждого метода и пример прогона conformance — в **[demo/docs/integration.md](demo/docs/integration.md)**. Готовая реализация, которую можно взять за основу — `demo/host/DemoHostAdapter.ts`.

## Проверить

```sh
cd contracts
npm test                 # 141 unit-тест
npx playwright test      # 4 браузерных теста
npm run typecheck
node scripts/check-boundary.mjs        # boundary: OK — пакет не зависит от demo/
npm run check:playwright-free          # ядро работает без @playwright/test

cd ../demo
npm test                 # typecheck + 84 unit-теста + 2 Playwright (conformance + end-to-end)
npm run examples:pack
cd ../contracts
for z in ../demo/examples/*/dist/*.zip; do npx vibe-plugin check "$z"; done   # каждый → ok
```

`npm run dev` из `demo/` поднимает оба origin одной командой. End-to-end сценарий проходит через реальные клики: загрузка двух версий плагина, два экземпляра, данные в `storage`, обновление и откат, изменение размеров панелей, роутинг приложения, back/forward, перезагрузка и «вредный» виджет, после которого хост продолжает работать.

Перед `npm test` порты 4000 и 4001 должны быть свободны: Playwright поднимает собственный сервер с чистым реестром и не переиспользует уже запущенный `npm run dev`.

## Ограничения

- **Node ≥ 24.** Подпути пакета указывают на `.ts`-исходники; на Node 20/22 понадобится отдельная сборка `contracts/` в JS.
- **CSP `script-src 'self' 'unsafe-inline'`.** `pack` вставляет синхронный inline-скрипт `__VIBE_BOOT__`, с которым строгий `script-src 'self'` несовместим. Изоляция плагина от хоста от этого не страдает (разные origin, sandbox, `connect-src 'none'`, `frame-ancestors`), но при использовании в продакшне скрипт стоит заменить на nonce/hash или внешний `boot.js`. Подробнее — в `integration.md`.
- **Изоляция плагинов друг от друга** на уровне origin не гарантируется: в демо у них общий `:4001` и общие `localStorage`/cookies этого origin. `getPluginOrigin(descriptor)` позволяет выдать каждому плагину отдельный origin без изменений в ядре.
- **Это демонстрационный проект.** Авторизация, БД, подпись кода, SSR, миграция схем данных плагина и серверная рассылка версий в него не входят. Production-режим хоста ожидает собранный `dist/index.html`; скрипта сборки хоста нет.
- **Известная мелочь.** Если плагин отклонён из-за несовместимой версии, через 10 секунд в его плитке дополнительно появится карточка «handshake timed out». На работу сценария это не влияет.
